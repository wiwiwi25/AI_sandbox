4. Publication diagnosis — why pushes stalled

The reported symptom was "the push hangs with no output, so credential.helper must be prompting invisibly". That reading was half right about the symptom and wrong about the cause: the stall was real, the invisible prompt was not Git Credential Manager.

4.1 Symptom

git push produced no output for the full timeout — 300 s, then again on a retry — while git ls-remote in the same shell returned in well under a second. Nothing appeared on stderr, so there was nothing to react to; the tool could only report that the process was still running.

Slow network, unreachable host GIT_CURL_VERBOSE=1 into a log file, then read the tail. Rejected TCP connect succeeded in milliseconds; the failure sits above the transport, not below it.

4.3 What was actually happening

Two independent faults sat on top of each other. Each one alone is enough to produce a silent stall:

  1. SSH with no key. git push resolves to SSH, but there is no private key, no agent, and no known_hosts. The first connection must therefore ask the host-key question — and that question is asked on the terminal, not on captured output. When the answer never arrives the client waits. SSH writes nothing to stdout, so to the caller the push is merely slow.
  2. A dead token on the HTTPS path. Addressing the same remote over HTTPS skips the SSH prompt but answers 401. With the credential helper disabled, Git has no way to obtain a password and no way to fail fast.

That pair explains every confusing observation: an HTTPS ls-remote that works (read-only, anonymous is enough on a public repository), an HTTPS push that cannot authenticate, an SSH ls-remote that fails instantly, and a push that prints nothing at all.

4.4 How the two commits were published anyway

A one-shot override, with no persistent change to the repository configuration:

git -c remote.origin.pushurl=https://github.com/wiwiwi25/AI_sandbox.git push origin main

This forces the push leg onto HTTPS, where an existing credential still authorises writes, while leaving remote.origin.url untouched. It was used for both 01bceb1 and 29e98b7. Its limitation is written into the document: a bare git push still fails until one of the three remedies in §4.5 is applied.

4.5 The three remedies recorded in §4.2

OptionActionEffectCost
AKeep passing -c remote.origin.pushurl=https://… on each push. Works today; nothing in the repo changes. Every push needs the flag; easy to forget and mistake for another stall.
Bgit remote set-url origin https://github.com/wiwiwi25/AI_sandbox.git Bare git push works with the stored credential. Changes .git/config (local only, not committed); token still governs writes.
Cssh-keygen -t ed25519, add the public key to GitHub, then ssh -T git@github.com to accept the host key. Keeps the SSH remote; no token in the credential store. Needs a GitHub account action and a first manual host-key confirmation.

Recorded state at the end of the session: the remote is still SSH, so option C is the only one that makes the existing configuration work; A and B both route around it.

5.2 §4.1 — demoted from "open" to done

§4.1 was the item "make sure no token is left in the repository". It is now closed, with the reasoning kept visible:

  • Token gone from .git/config: the file's [remote "origin"] section contains an SSH URL, no https://<token>@ form.
  • No token in any commit: a history scan over all commits returns nothing for the credential pattern — the earlier HTTPS URL lived only in local config.
  • But the 401 is not proof of revocation. A revoked token, an expired token, a token without repo scope and a token belonging to another account all produce the same response. The document says "consistent with revocation", and asks the user to confirm at github.com/settings/tokens before the stronger claim is written.

That distinction is the point of the item: a fact that can only be confirmed outside the repository is labelled as such instead of being upgraded to certainty on the way into the log.

5.4 Why the row is 3.1 and not 2.2

The instruction asked for "revision 2.2". That number is already taken: the history table contains 1.0 → 2.0 → 2.1 → 2.2 → 2.3 → 3.0, each row a one-line account of a real edit. Appending a second 2.2 below 3.0 would break two invariants the document states about itself — the table is append-only and it is ascending — and would leave two different contents under one version number.

So the row is 3.1: a revision of 3.0, which is what it is. The decision was stated before the commit and is repeated here and in the revision row itself, because a silent renumbering would be exactly the kind of undocumented drift the document is trying to eliminate. The same reasoning changed the commit subject from "append revision 2.2" to "append revision 3.1" — the Commit column quotes the subject, so the two must agree.
