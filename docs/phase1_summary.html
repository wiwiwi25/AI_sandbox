Why the worktree is 28/10. The index is what Git enforces and what a clone reproduces — 38/38 LF. The worktree is whatever each editor last wrote; git add normalises on the way in, which is the warning: CRLF will be replaced by LF line seen when staging. That warning is the mechanism working, not a violation: the committed blob is LF.

The trap, in one sentence: Rojo writes the API-dump defaults for every declared service, and Studio applies whatever the built place contains — so a property that appears in neither src/ nor the project file is invisible to every tool in the gate. Hence A2 and A17, and hence the rule: change default.project.json → rebuild before playing. Studio plays the place, not the project.

4. Handoff and next steps

Disposable by design: it describes what the next session should do and is replaced wholesale. Ordered by cost-of-late, so a security item is first and tidy-ups are last.

4.1 The token is out of .git/config done

  • Measured: remote.origin.url is git@github.com:wiwiwi25/AI_sandbox.git and no token literal exists in .git/config — the credential-bearing HTTPS URL that 2.x described is gone.
  • It does not authenticate either: HTTP/1.1 401 Unauthorized on git-receive-pack. Consistent with revocation, but not proof — a deleted token and a live read-only token fail identically. Confirm at github.com/settings/tokens, delete anything unused.
  • Removing the URL was hygiene; the copy on disk was the exposure — anything that could read the file, including anything that echoed the remote. A token written to disk should be assumed read.
  • Never committed: .git/ is outside the tree; git grep -nE 'ghp_[A-Za-z0-9]{20,}' returns nothing.

4.2 Publication state push is blocked

  • Published and verified: 01bceb1 is origin/main — checked with git ls-remote <https-url> refs/heads/main, not inferred from ahead 0.
  • The remote moved to SSH — git@github.com:…, fetch and push — and it cannot authenticate here: no ~/.ssh key, no agent, and ssh -T git@github.com answers Permission denied (publickey). An empty known_hosts blocks even earlier, on a host-key question that never reaches the terminal.
  • The silent hang is SSH, not the credential helper. No GitCredentialManager process runs during a push, and SSH writes nothing to stdout, so a stalled push looks exactly like a slow network. Check Get-Process git for stale processes before blaming either — seven were alive at once this session.
  • The old token is dead — HTTP/1.1 401 Unauthorized, twice — so -c credential.helper= cannot help: it removes the only thing that could answer, and git then waits on a Username: prompt nobody can see. Clearing the helper makes pushing worse, not cleaner.
  • HTTPS + GCM is the path that works. credential.helper=manager at system scope authenticated non-interactively while 3.1 was published; a one-shot pushurl leaves remote.origin.url alone and still advances origin/main.
  • Never amend, never force-push. df56a1c, 8d9ebaf and 01bceb1 are public; a rejected push is rebased, not overwritten. A file cannot cite its own hash — find it by subject with git log --grep.
Three ways to restore pushing, and one flag to stop it hanging 
# A. publish now without touching .git/config; origin/main stays accurate
git -c remote.origin.pushurl=https://github.com/wiwiwi25/AI_sandbox.git push origin main

# B. or make HTTPS the remote — GCM then prompts once, in a visible window
git remote set-url origin https://github.com/wiwiwi25/AI_sandbox.git

# C. or make SSH work: create a key, register it, verify; the remote needs no change
ssh-keygen -t ed25519; ssh -T git@github.com

# fail fast instead of hanging, for any of the three
$env:GIT_SSH_COMMAND='ssh -o BatchMode=yes -o ConnectTimeout=10'; $env:GIT_TERMINAL_PROMPT='0'
