How this document is maintained. It is a living file, and each part has exactly one rule:

  • §1 and §2 are snapshots of the state at the timestamp above. When the state changes, refresh them in place and bump document-version.
  • §3 is append-only. A new session adds a new dated entry below the last one. An existing entry is never edited or deleted, even when it later turns out to be wrong — a correction is a new entry that says so.
  • §4 is disposable. It is the handoff the next session works from, and it is expected to be replaced wholesale rather than preserved.
  • §5 is append-only as well, and is where the document's own revisions are recorded.

There are exactly two append points, both marked with an HTML comment in the source: <!--@ NEXT SESSION ENTRY --> at the end of §3 and <!--@ NEXT REVISION ROW --> at the end of §5. A session that changes the state reads §2, appends to §3, rewrites §4 and logs the change in §5 — in that order.

1. Executive summary

CursedGems Phase 1 was code-complete before this session and had no version control whatsoever. Everything below follows from fixing that one gap: the project is now a repository, the repository is published, and the two documents that describe it no longer describe it wrongly. The code itself did not change — not a line — and that is the point.

QuestionBefore this sessionNow
Where does the project live? One folder on one Windows machine. tools/, build/ and the generated sourcemap.json sat in it indistinguishably from real source. A Git repository in which 37 files are the project and 64.0 MB of toolchain plus every generated artifact are excluded by rule.
Can a mistake be undone? No. There was no history, so there was nothing to diff and nothing to revert to. One root commit df56a1c, published to origin/main. Every change from here is a diff.
Who authored it? Whatever identity the machine happened to carry. A repo-local user.name and a GitHub noreply address, so no real email address is published and nothing global was touched (there is no ~/.gitconfig at all).
Does the documentation match the artifact? It said the Rojo defaults trap touched 38 services, and called the toolchain "vendored, so a fresh clone needs no downloads". 5 declared services carrying 35 items, with the two proof properties quoted from the built place; 64.0 MB measured, and the trade-off written into the architecture document instead of assumed.
How is it accepted? Sixteen Track A checks. Chat was not one of them, even though chat depends on a property that lives in the project file. Seventeen checks, with A17 covering chat and each project-file property cross-referenced to the check that proves it.
Is it known to work? No playtest had been recorded. Still no playtest recorded. This session fixed the infrastructure around the acceptance run, not the acceptance run.

The two things worth remembering

One: two properties live in the project file, not in src/. Players.CharacterAutoLoads and TextChatService.ChatVersion are written into the built place by Rojo at the API dump's default unless the project declares them. The defaults contradicted this design: characters would have auto-loaded before player state did, and chat would have run the legacy implementation. Neither is a code bug, neither is visible to the gate, and both are now declared explicitly and checked by hand (A2 and A17).

Two: the documentation had drifted, in the flattering direction. It over-counted the Rojo symptom by seven times (38 services against 5 actually declared) and under-reported the vendored toolchain by about 2.5 times (an earlier estimate of ~26 MB against 64.0 MB measured). Both are now stated as measurements with the commands that produce them, which is the only form a future reader can check.

A third, smaller drift is left visible rather than fixed: .cursorignore and the header comment of .gitignore both describe the project as "the ~2,500 lines that are actually this project". The measured figure is 5,775 physical lines in src/ (4,627 of them code), plus ~1,500 lines of documentation. The number was true at some earlier point and stopped being true; it is logged in §4.7 rather than quietly corrected in this commit, because a log that silently edits other files is not a log.

What this does not mean

Nothing here closes a gate criterion. G1–G6 in the playtest document are still open, the seventeen Track A checks still have no recorded results, Track B has never run, there is no version tag, no licence, no CI and no behavioural test. Phase 1 is code-complete and properly versioned, not accepted. §4 is what turns the first into the second.

2.3 Line endings

The project is developed on Windows and stored as Unix-convention files. That is not a preference — the gate fails on it: check.ps1 runs stylua --check, and .stylua.toml pins line_endings = "Unix". Git for Windows installs with core.autocrlf=true, which would check these sources out as CRLF and fail step 1 of the gate on a fresh clone, on files nobody edited. So the attribute is forced rather than left to text=auto. .gitattributes in full:

.gitattributes — 897 bytes, verbatim 
# ============================================================================
#  CursedGems :: line endings and binary files
# ============================================================================
#  The gate runs `stylua --check`, and .stylua.toml pins line_endings = "Unix".
#  Git for Windows installs with core.autocrlf=true, which would check these
#  sources out as CRLF and fail step 1 of check.ps1 on a fresh clone. Pin LF in
#  the index *and* the working tree so a clone is byte-identical to this one.
#
#  The project is developed on Windows but the files are Unix-convention; that
#  is why this is forced rather than left to `text=auto` alone.
# ============================================================================

* text=auto eol=lf

# Never let Git "normalise" a place file or a model.
*.rbxl  binary
*.rbxlx binary
*.rbxm  binary
*.rbxmx binary

And the other half of the same contract, .stylua.toml (178 bytes, verbatim):

column_width = 100
line_endings = "Unix"
indent_type = "Spaces"
indent_width = 4
quote_style = "AutoPreferDouble"
call_parentheses = "Always"
collapse_simple_statement = "Never"
LayerRuleMeasured now

Formatterline_endings = "Unix" in .stylua.toml Gate step 1, stylua : clean

Why the working tree is not uniformly LF. The index is what Git enforces and what a clone reproduces, and it is uniformly LF. The working tree is whatever each editor last wrote, and editors on Windows write CRLF; git add normalises on the way in, which is exactly what the warning below reports. Seen verbatim while staging this file:

warning: in the working copy of 'docs/phase1_summary.html', CRLF will be replaced by LF the next time Git touches it

That warning is the mechanism working, not a violation: the committed blob is LF, and git ls-files --eol prints i/lf w/crlf for this file rather than a diff. If a future session wants a byte-identical working tree as well, git add --renormalize . followed by a fresh checkout is the one-liner.

2.5 The project file, and the trap it hides

default.project.json is the only place the Roblox tree is declared. Rojo writes the API dump's defaults for every service the project declares, not just the tree — so a property the project never mentions is serialised at the dump's value rather than at Studio's new-place value, and Studio applies whatever is in the file when it opens. 3.1 How to append an entry

  1. Measure first. Run .\check.ps1 and re-derive any number you intend to quote — see the checklist in §5.2. A remembered number is the one thing this document has already been wrong about twice.

  3. Number it session.entry — for example 2.1 — and never reuse a number. The session number comes from the index below.
  4. Add a row to the session index (§3.2) for a new session, or extend that session's row if the entry continues the same one.
  5. If the state changed, refresh §2 and the JSON block in §2.6, bump document-version in the head, and add a revision row in §5.
  6. Validate before committing — the four commands in §5.2 — then stage, commit and push.
  7. Rewrite §4. It is the handoff, it is disposable, and it should describe what the next session should do, not what the last one did.

4.1 First: revoke the token sitting in .git/config

While auditing the remote, one finding did not belong to the repository at all. On this machine, .git/config stores origin in the form https://<token>@github.com/wiwiwi25/AI_sandbox.git — a GitHub personal access token in plaintext, in the repository's own configuration file. The token value is deliberately not reproduced in this document, and this report is not the place to look for it.

QuestionAnswer
Is it in any commit? No. .git/ is never part of the tree. git grep -nE 'ghp_[A-Za-z0-9]{20,}' returns nothing, and the pushed history contains no credential.
Who can see it? Anything running on this machine that can read .git/config — editors, scripts, agents, and any terminal where the URL is echoed.
Does publishing make it worse? No, but it does not make it better: the token predates the repository and its scope is whatever it was created with.
What fixes it? Revoking it. Rewriting the URL is hygiene, not remediation — a token that has been written to a file should be assumed to have been read.
  1. Revoke the token at github.com/settings/tokens. Do this before anything else in this section.
  2. Rewrite the remote without credentials:
git remote set-url origin https://github.com/wiwiwi25/AI_sandbox.git
git remote -v
origin  https://github.com/wiwiwi25/AI_sandbox.git (fetch)
origin  https://github.com/wiwiwi25/AI_sandbox.git (push)
  1. Confirm the next push still authenticates. Removing the inline token removes a stored credential, not the ability to authenticate: Git falls back to the configured credential helper, and at worst prompts once (see §4.2 for what that helper is on this machine).
  2. If a token is needed again, let the helper store it, or use gh auth login — never put it back into a URL.

This is logged as an action item rather than silently repaired because the repair is revocation at GitHub, which only the account holder can do. Rewriting the URL here would have made the file look clean while leaving a live credential valid.

5.2 Protocol — measure, write, validate, commit

Four steps, in this order. The first is the one this document has already failed at twice.

  1. Measure before quoting. Any number in this file should be reproducible by a command printed next to it. If you cannot find the command, do not quote the number.
